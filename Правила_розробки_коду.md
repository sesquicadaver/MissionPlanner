# Правила розробки коду

## 1. Загальний принцип

Код має бути:

```text
простий → модульний → тестований → передбачуваний → безпечний
```

Будь-яке ускладнення допускається лише після доведеної технічної необхідності.

---

## 2. Мінімалізм

1. Не додавати абстракцію без мінімум двох реальних місць використання.
2. Не створювати “універсальні” механізми наперед.
3. Не писати код “на майбутнє”.
4. Не дублювати логіку.
5. Не створювати helper/service/manager без чіткої відповідальності.
6. Видаляти мертвий код одразу.
7. Заборонені заглушки без `TODO` з номером задачі.
8. Заборонені “тимчасові” рішення без терміну видалення.

---

## 3. Модульність

Кожен модуль має мати одну відповідальність.

```text
правильно:
link_manager
params_service
mission_service
telemetry_store

неправильно:
utils
common
helpers
manager
misc
```

Правила:

1. Модуль не повинен знати про UI, якщо він backend.
2. UI не має доступу до serial/MAVLink напряму.
3. Бізнес-логіка не має залежати від rendering/API layer.
4. Залежності мають іти всередину, а не назовні:

```text
ui → api_client → daemon
daemon → core
core → domain types
```

5. Domain-моделі не імпортують transport/storage/UI.
6. Кожен публічний API модуля має бути мінімальним.

---

## 4. Читабельність

1. Імена мають пояснювати призначення без коментарів.
2. Функція виконує одну дію.
3. Максимальна довжина функції: 40 рядків.
4. Максимальна кількість аргументів: 4.
5. Вкладеність не більше 3 рівнів.
6. Ранні `return` дозволені й бажані.
7. Складні умови виносити в named predicates.

```rust
// погано
if vehicle.armed && !link.stale && mode == Guided && battery > 20 {}

// добре
if can_start_mission(&vehicle, &link, &power) {}
```

---

## 5. Архітектурна чистота

Заборонено:

1. Global mutable state.
2. Singleton як прихована залежність.
3. Circular dependencies.
4. God object.
5. “Manager”, який керує всім.
6. Side effects у конструкторах.
7. Blocking IO в async runtime.
8. Silent failure.
9. Catch-all error handling без контексту.
10. UI-driven business logic.

---

## 6. Помилки

1. Кожна помилка має мати контекст.
2. Помилки не ігноруються.
3. `unwrap()` заборонений у production-коді.
4. `expect()` дозволений лише з поясненням інваріанта.
5. Panic допустимий тільки при порушенні неможливого інваріанта.
6. Recoverable error не може бути panic.
7. Користувацькі помилки і системні помилки мають розрізнятися.

```rust
thiserror → domain errors
anyhow → application boundary
```

---

## 7. Async / concurrency

1. Усі IO-операції — async.
2. Нема blocking sleep.
3. Нема busy loop.
4. Shared state тільки через:

   * message passing;
   * bounded channels;
   * immutable snapshot;
   * explicit lock з мінімальною зоною.
5. Lock не тримати під час `.await`.
6. Кожна background task має:

   * lifecycle;
   * cancellation;
   * timeout;
   * structured logging.

---

## 8. API між модулями

1. API має бути явним.
2. Команди і події розділяються.

```text
Command = намір змінити стан
Event   = факт, що вже стався
Query   = читання стану
```

3. Команда не повертає “магічний bool”.
4. Результат команди:

```rust
Result<CommandAck, CommandError>
```

5. Події immutable.
6. Подія не виконує дію.

---

## 9. Policy-gate

Жоден небезпечний effect не виконується напряму.

```text
request
→ validate
→ policy_check
→ execute
→ audit_log
```

Обов’язково через policy-gate:

* arm/disarm
* mode change
* mission upload
* parameter write
* firmware flash
* reboot
* actuator test
* motor test

---

## 10. Логування

1. `println!` заборонений у production-коді.
2. Використовувати structured logging.
3. Кожна важлива дія має `trace_id`.
4. Логи мають відповідати рівню:

```text
TRACE — внутрішній потік
DEBUG — діагностика
INFO  — нормальна значуща дія
WARN  — деградація
ERROR — помилка операції
```

5. У логах не має бути секретів.
6. Помилки логуються один раз на boundary.

---

## 11. Конфігурація

1. Жодних hardcoded runtime parameters.
2. Значення за замовчуванням мають бути явно задокументовані.
3. Конфіг валідується при старті.
4. Некоректний конфіг → fail-fast.
5. Runtime override має бути явним.
6. Конфіг не читається хаотично з різних місць.

---

## 12. Тести

Обов’язково:

1. Unit tests для pure logic.
2. Integration tests для сервісів.
3. SITL tests для MAVLink workflows.
4. Regression tests для кожного виправленого bug.
5. Property-based tests для parser/serializer.
6. Fault-injection tests для link loss, timeout, reconnect.

Мінімальне правило:

```text
нема тесту → нема merge
```

---

## 13. Структура файлів

```text
module/
  mod.rs
  types.rs
  service.rs
  errors.rs
  tests.rs
```

Або для більшого модуля:

```text
module/
  mod.rs
  domain/
  service/
  transport/
  storage/
  tests/
```

Заборонено:

```text
utils.rs
helpers.rs
common.rs
misc.rs
```

Дозволено лише якщо файл має вузьке доменне ім’я:

```text
crc.rs
mavlink_frame.rs
param_codec.rs
mission_diff.rs
```

---

## 14. Коментарі

Коментар пояснює “чому”, а не “що”.

```rust
// погано
// increment counter
counter += 1;

// добре
// ArduPilot may resend PARAM_VALUE after timeout; keep idempotent.
apply_param_value(msg);
```

Заборонені коментарі, що дублюють код.

---

## 15. Naming

1. Назви мають бути доменні.
2. Скорочення заборонені, крім стандартних:

```text
gps, ekf, imu, mavlink, udp, tcp, uart
```

3. Boolean має читатися як твердження:

```rust
is_armed
has_gps_fix
can_upload_mission
should_reconnect
```

4. Функція має починатися з дієслова:

```rust
download_params()
validate_mission()
record_telemetry()
```

---

## 16. Rust-specific

Заборонено:

```rust
unwrap()
todo!()
unimplemented!()
dbg!()
unsafe
```

`unsafe` допускається лише:

* в окремому модулі;
* з safety comment;
* після code review;
* з тестами.

Правила:

1. Prefer ownership over cloning.
2. Clone тільки явно і обґрунтовано.
3. Public types мінімальні.
4. `pub(crate)` замість `pub`, якщо можливо.
5. Traits тільки для реальної поліморфності або тестування.
6. Не використовувати macro без потреби.

---

## 17. QML/Qt-specific

1. QML тільки для presentation layer.
2. Бізнес-логіка не пишеться в QML.
3. QML-компонент ≤ 250 рядків.
4. Великі екрани розбивати на компоненти.
5. State management централізований.
6. UI не виконує MAVLink-команди напряму.
7. Усі команди йдуть через API client.

---

## 18. Git rules

1. Один commit = одна логічна зміна.
2. Commit message:

```text
type(scope): summary
```

Приклади:

```text
feat(link): add serial reconnect policy
fix(params): handle duplicate PARAM_VALUE
test(mission): add upload timeout regression
```

3. Заборонені commits:

```text
fix
update
wip
misc
changes
```

4. Перед merge:

```text
cargo fmt
cargo clippy
cargo test
integration tests
```

---

## 19. Definition of Done

Задача завершена лише якщо:

```text
код реалізовано
тести додано
логи коректні
помилки оброблені
конфіг валідований
документація оновлена
нема dead code
нема TODO без task id
нема clippy warnings
нема форматування поза стандартом
```

---

## 20. Головне правило

```text
Якщо код неможливо швидко прочитати, протестувати і безпечно змінити — код неправильний.
```
